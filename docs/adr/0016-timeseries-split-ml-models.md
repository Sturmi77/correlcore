# ADR-0016 — Time-Series Split Strategy for Machine Learning Models

**Status:** Accepted  
**Date:** 2026-05-11  
**Milestone:** M7 (Insights v2)  
**Decider:** Solo developer  
**Related Issues:** #144, #145, #146, #149, #150

---

## Context

M7 introduces machine learning models to the analytics pipeline: Lasso regression, lag analysis, weekday confounder control, and changepoint detection. These models require validation to ensure they generalise to unseen data and produce reliable insight statements.

The standard cross-validation technique in scikit-learn is `KFold`, which randomly shuffles observations into training and test folds. For **time series data**, this is statistically invalid:

- A fold may contain entries from week 10 in the _training_ set and entries from week 8 in the _test_ set.
- The model therefore "learns from the future" — a form of data leakage known as **look-ahead bias**.
- Look-ahead bias produces artificially high cross-validation scores and overfitted models that fail in production.

CorrelCore mood entries are inherently temporal: `entry_date` is an ordered, non-exchangeable index. Any model that uses historical entries to predict future mood must respect this ordering.

---

## Decision

**All cross-validated ML models in the analytics pipeline must use `TimeSeriesSplit` from scikit-learn instead of `KFold` or `ShuffleSplit`.**

```python
from sklearn.model_selection import TimeSeriesSplit

tscv = TimeSeriesSplit(n_splits=5)
```

`TimeSeriesSplit` creates folds that always use _earlier_ observations for training and _later_ observations for testing, respecting the causal direction of time:

```
Fold 1:  Train [t1 … t18]      Test [t19 … t36]
Fold 2:  Train [t1 … t36]      Test [t37 … t54]
Fold 3:  Train [t1 … t54]      Test [t55 … t72]
...
```

No future observation is ever present in a training fold that precedes it.

### Corollary: Lag Feature Integrity

When lag features are constructed (Issue #145), `DataFrame.shift(lag)` introduces `NaN` values in the first `lag` rows. These rows **must be dropped with `df.dropna()`** before any model training or validation. Filling `NaN` with 0 is forbidden — it implicitly asserts "nothing happened before the observation window started", which is a false assumption that biases coefficients downward.

```python
# CORRECT
for lag in range(1, MAX_LAG_DAYS + 1):
    df[f'{col}_lag{lag}'] = df[col].shift(lag)
df = df.dropna().copy()  # causal integrity: first MAX_LAG_DAYS rows removed

# WRONG
df = df.fillna(0)  # introduces false zeros — prohibited
```

### Corollary: Analytics Worker Data Loading

All data loading in the analytics worker must sort and filter by `entry_date`, not by `created_at` or `updated_at`. Users can backfill entries up to 7 days in the past (DESIGN_DOCUMENT §2.1); a backdated entry has `created_at` later than its `entry_date` position in the time series.

```python
# CORRECT
entries = (
    session.query(Entry)
    .filter(Entry.user_id == user_id)
    .filter(Entry.entry_date < date.today())
    .order_by(Entry.entry_date.asc())
    .all()
)

# WRONG
# .order_by(Entry.updated_at.asc())  — introduces look-ahead bias
```

## Alternatives Considered

### Option A: `KFold` (rejected)

**Pros:** Simpler; produces more folds with smaller datasets.  
**Cons:** Allows future data to appear in training folds. Produces invalid cross-validation scores on temporal data. Would give a false sense of model quality. **Rejected.**

### Option B: `ShuffleSplit` (rejected)

**Pros:** Flexible train/test ratio; can handle unbalanced datasets.  
**Cons:** Same look-ahead bias problem as `KFold`. **Rejected.**

### Option C: Walk-Forward Validation (considered, deferred)

Also called _expanding window_ or _anchored walk-forward_. Train on all data up to point T, test on point T+1, advance by one observation. Produces n-1 folds for n observations, maximising statistical power.

**Pros:** Most rigorous temporal validation.  
**Cons:** Very slow for large datasets; high computational cost in a nightly batch worker; overkill for datasets of ~90–500 entries. Can be reconsidered post-M7 if model quality becomes a concern.  
**Deferred to post-M7 review.**

### Option D: Single train/test split with holdout (considered, deferred)

Reserve the last 20% of entries as a holdout test set, train on the first 80%.

**Pros:** Simple; zero leakage risk; easy to explain.  
**Cons:** Wastes data; no variance estimate on model quality; not robust for users with exactly 90 entries (18 test entries is insufficient). **Deferred.**

---

## Consequences

### Positive

- Cross-validation scores are statistically valid and will be lower than with `KFold` — this is expected and desirable.
- Insights generated by Lasso are based on genuinely out-of-sample validation, increasing user trust.
- The approach generalises to all future ML additions to the analytics pipeline without case-by-case decisions.

### Negative

- `TimeSeriesSplit` requires a minimum number of entries to produce `n_splits=5` folds with meaningful size. **Minimum n=90 entries** enforced in the M7 worker before any cross-validated model is run.
- Slightly more verbose setup than `LassoCV()` with default `cv=5`.

### Neutral

- `statsmodels` OLS models (Issue #146 weekday confounder) do not use cross-validation. This ADR does not apply to them. They use Newey-West HAC standard errors to handle temporal autocorrelation in residuals instead.
- `ruptures` changepoint detection (Issue #149) does not use cross-validation. PELT is a penalised exact search; the penalty hyperparameter is set by BIC heuristic, not CV.
