## Findings that change the scope

Two things surfaced while reading the code that the issues do not account for.
Both should be settled before implementation starts.

### F1 — #490's premise is wrong at the data level

The issue says a high percentage fill reads wrong for `reduce` habits
(“mehr = besser”). That is not what the data does. `_adherence_rate` in
[`habit_service.py:54`](../../backend/app/services/habit_service.py) already
normalises both types so **100 always means “doing well”**:

```python
if habit_type == "build":
    return min(100, days_tracked / target_days * 100)
# reduce: at or under target → 100.0, decaying as you exceed
```

So a full bar on a reduce habit means “stayed within the limit”, which is
correct. Implementing the issue's MVP literally — _“Reduce = invertiertes oder
hohles Fill”_ — as an inverted **value** would make a well-managed reduce habit
show an almost empty bar. That is a regression, not a fix.

**The real defect is different:** the same bar carries two different meanings
(progress _toward_ a target vs. headroom _under_ a limit) and nothing but muted
text distinguishes them. The fix is to encode the _kind_, not to invert the
_value_.

**Recommendation:** keep “fuller = better” for both types. Differentiate through
shape, texture and a glyph. This needs sign-off before UI work starts, because
it contradicts the issue text.

### F2 — #487 must canonicalise tags or it will split counts

#485 established that copy-on-write tag overrides share a slug with the default
row but carry a different id, and that analytics must collapse them —
`canonicalize_tags_by_slug` in
[`tag_service.py:133`](../../backend/app/services/tag_service.py), already used
in three places in `stats_service.py`.

A naive `GROUP BY tag_id` for the weekday top signal would count a user's
renamed “Meeting” separately from the default “Meeting” and could hand the
weekday to the wrong signal. The new aggregation must reuse the same helper.

## #487 — Weekday top signal

### Current state

`GET /dashboard/summary` returns `weekday_summary` with `weekday`,
`entry_count`, `mood_avg` only
([`schemas/dashboard.py:20`](../../backend/app/schemas/dashboard.py)).

The frontend cell type **already has a finding slot** —
`findingLabel` / `findingType` in
[`homeWeekdayOverview.ts:7`](../../apps/web/src/lib/utils/homeWeekdayOverview.ts) —
currently fed opportunistically from insight confounders, and rendered in
[`HomeWeekdayOverview.svelte:65`](../../apps/web/src/lib/components/home/HomeWeekdayOverview.svelte).
That is a real head start: no new UI slot is needed, only a better source.

### Steps

**1. Backend schema** — add to `WeekdaySummaryItem`:

```python
class WeekdayTopSignal(BaseModel):
    kind: Literal["tag", "symptom", "work_context"]
    id: uuid.UUID | None = None
    label: str
    count: int
    share: float  # count / weekday entry_count

top_signal: WeekdayTopSignal | None = None
```

Optional field — no breaking change for existing clients.

**2. Backend aggregation** in `dashboard_service.get_dashboard_summary`:

- Reuse the existing window (`entry_date <= as_of`, `slot == DAY`) and the
  existing `MIN_WEEKDAY_ENTRIES = 7` gate, so the new field appears exactly when
  `weekday_summary` does.
- Three counts per weekday, over `entry_tags`, `entry_symptoms`,
  `entries.work_context`.
- **Collapse tag aliases via `canonicalize_tags_by_slug` (F2) before counting.**
- Tie-break per the issue: tag > symptom > work_context, then label.
- Emit `None` when the winner is too thin — propose a floor of
  `count >= 2 and share >= 0.3`, otherwise a single stray entry becomes “what
  typically happens on Mondays”. **This threshold is a product call** and is not
  specified in the issue.

Prefer one grouped query per source over per-weekday loops; the dashboard
endpoint is on the Home path and already runs several queries.

**3. Web types + mapping** — extend `WeekdaySummaryItem` in
[`api/dashboard.ts`](../../apps/web/src/lib/api/dashboard.ts), then in
`buildWeekdayOverviewCells` prefer `top_signal` over the insight-confounder
finding, keeping the confounder as fallback. Map `kind` → existing
`findingType` union (`tag` | `symptom` | `context`), which already drives
`data-type` styling.

**4. i18n** — DE/EN for the label wrapper (e.g. “meist: {label}”). The signal
label itself is user data and is not translated.

**5. Tests**

- Backend: aggregation picks the mode per weekday; tie-break order; alias
  collapse (a default + override pair for one slug counts as one); `None` below
  threshold; field absent when `weekday_summary` is empty.
- Web unit: `top_signal` wins over confounder; fallback when absent; `kind`
  mapping.
- Extend existing dashboard mocks — several specs construct
  `DashboardSummaryResponse` literals and will need the optional field only if
  typed strictly.

### Risk

Extra queries on the Home critical path. Mitigate by folding the three counts
into one `UNION ALL` grouped query, and confirm the endpoint's response time
does not regress noticeably on a seeded dataset.

### Estimate

Backend 0.5–1 day, frontend 0.5 day, tests 0.5 day. **~2 days**, dominated by
getting the aggregation right rather than by UI.

## #490 — Habit build vs reduce encoding

### Current state

Both types render the identical primary bar:
`HabitsPanel.svelte:243` (`--habit-progress`) and `HabitDetailBody.svelte:86`,
both driven by `habitProgressValue`
([`habitMetrics.ts:47`](../../apps/web/src/lib/utils/habitMetrics.ts)). Type
appears only as muted text via `habits.type.{habit_type}`.

### Steps — MVP (presentational only)

Given F1, the value stays as is. Differentiate the encoding:

**1. Type-aware meter.**

- `build` — solid fill, left→right, unchanged from today.
- `reduce` — same direction and same value, but a visually distinct
  treatment: hollow/outlined track with a hatched or lighter fill, so it
  reads as “headroom used” rather than “progress made”.
- Add a `+` / `−` glyph before the label. No red/green — forbidden by
  [`COLOR_SCHEME_CONCEPT.md`](../frontend/COLOR_SCHEME_CONCEPT.md).
- Must pass `pnpm check:style-tokens`, `check:style-contract` and the
  contrast job; use existing tokens only.

**2. List grouping** — “Building” / “Reducing” sections or chips in
`HabitsPanel`. Sections are the safer choice: chips imply filtering, which is
not in scope.

**3. Accessible text** — the meter carries `aria-label` including the type, so
the distinction is not colour/texture-only. This is the part most likely to
be missed and is a WCAG requirement, not a nicety.

**4. i18n** — DE/EN for section headings and the type glyph label.
Vocabulary stays `reduce`, not “avoid”.

**5. Tests + QA** — web unit on the type→encoding mapping; visual QA rows for
light/dark and mobile/desktop. Include a reduce habit that is **over** its
limit, since that is where the encoding has to stay legible.

### Phase 2 — “Strahl” (separate issue, not in this scope)

The radial spoke widget from the issue is net-new SVG with its own layout,
animation and a11y story. Recommend shipping the MVP first and only opening a
follow-up if the type distinction still tests poorly. The issue itself frames it
as conditional (“wenn MVP nicht reicht”).

### Estimate

**~1 day** including tests, assuming F1 is settled. Purely frontend, no API or
schema change.

1. **Settle F1** — one decision, blocks #490's UI work.

aggregation work is still being designed.
